## Решения Q1–Q8

- Q1: пакет параллельных услуг отложен; overlapping_services не подтверждается.
- Q2: rejected и needs_confirmation блокируют Analyze; inactive не блокирует, причина видна.
- Q3: при импорте поверх непустой реальной session требуется подтверждение Replace audit с перечислением замены расходов/решений/reported savings/цели. Cancel ничего не меняет. Это часть frontend-интеграции группировки.
- Q4: после Analyze нужен повторный импорт. Preview между маршрутами не сохраняется; UI не обещает восстановление. Это цена минимального варианта без расширения хранения.
- Q5: необязательный name оставлен; имя — подпись результата, не доказательство частоты или активности.
- Q6: Merge разорванных частей ограничен confidence medium, без выдуманной истории.
- Q7: смена mapping очищает назначения и подтверждения с пояснением. overrides/skipped сохраняют существующее поведение.
- Q8: единый порог >1.5× для принудительного соединения частей; прежний автоматический k=1-путь не меняется.

## Обязательные поправки к Draft

1. Подтверждение только по rawIndices и large_price_change устаревает при Edit даты/суммы без смены индексов. Приняты proposalKey, confirmedFor и confirm.proposalKey; ключ зависит от текущих данных предложения, не от случайных Expense.id/времени. Engine проверяет совпадение. UI сбрасывает подтверждения при Edit/Exclude/Restore. Нужны unit/E2E на прежний набор индексов с новыми ценами и Exclude → confirm → Restore.
2. Merge разных normalized names использует единый внутренний ключ после глобального исключения refunds/credits/dedup. Нельзя повторно разбить корзину по старым именам или собирать Merge только из уже выпущенных Expense: часть NFLX могла вообще не дойти до Expense.
3. sources строится при выпуске расхода по фактическим объектам/sourceIndex. Неуникальный банковский ID не идентичность строки. Неоднозначный sourceIndex не выбирается молча. Перестановки не меняют источники при сохранённых sourceIndex.
4. Движок не знает о строках, не переданных адаптером: они получают unknown_row. row_excluded относится к переданным, но отфильтрованным refund/credit/exact duplicates. UI может уточнить текст своей диагностики.
5. Только applied-группы исключают строки из автоматического пула. Другие статусы не теряют данные и не удваивают расход.
6. Backend сначала реализуется целиком и проходит приёмку; затем Gemini делает UI/адаптер/E2E. Stub с applied без реального изменения состава не передаётся как готовая реализация.

Все решения внесены в docs/design/manual-grouping-contract.md; §14 имеет приоритет при неоднозначности. Публичный контракт заморожен для следующего задания.
