## Проблемы высокой важности

### F01 Разные услуги поставщика объединяются и занижают годовой расход

ТЗ: FR-06, FR-09, §7.2, §8.1. Вердикт: реализация расходится с ТЗ. Подтверждено выполнением функций.

Вход: три месяца подряд в один день оплачиваются `ADOBE PHOTOSHOP` по $9.99 и `ADOBE ACROBAT` по $19.99. У всех шести транзакций разные ID. Ожидаются две услуги с совокупным годовым расходом $359.76.

Получено: одна позиция `Adobe`, high confidence, цена $9.99, recurring $119.88/year. Второй расход $239.88/year исчезает из итогов. Порядок входных строк может влиять на выбранную цену.

Причина: нормализатор убирает различия услуг; если календарь всего поставщика подходит под частоту, `wholeFits` обходит разделение по сумме. Затем `dayAmounts` берёт только первую транзакцию за день. Для этих разных сумм даже не появляется duplicate flag.

Доказательства: [normalize.ts:18](/Users/nuras/Desktop/businesscup/src/lib/engine/normalize.ts:18), [detect.ts:137](/Users/nuras/Desktop/businesscup/src/lib/engine/detect.ts:137), [detect.ts:273](/Users/nuras/Desktop/businesscup/src/lib/engine/detect.ts:273). Отдельно подтверждено: `YOUTUBE TV`, `YOUTUBE MUSIC` и `YOUTUBE PREMIUM` превращаются в `YouTube Premium`.

Исправление: сохранить различия продуктов, разделять независимые серии до определения cadence, не сворачивать все списания за день в одну цену. При неоднозначности показывать Review и давать разделить группу. Приёмка: две параллельные серии сохраняют обе цены и сумму; переименование одной услуги не объединяет её с другой; настоящее изменение тарифа остаётся одной серией с price change.

### F02 Смена решения сохраняет завершение старого действия и искажает reported

ТЗ: FR-08, FR-09, FR-10, §8.1–8.2. Вердикт: реализация расходится с ТЗ. Подтверждено через store и computeTotals.

Сценарий: интернет $75/month → Negotiate с target $60 → Completed с фактической ценой $60 → изменить решение на Cut.

Получено: `decision=cut`, но `actionStatus=completed` и `reportedNewPriceCents=6000` остаются от переговоров. Results показывает reported $180/year; карточка Cut при этом выводит новую цену $0 и reported $900/year. Новый Cut фактически ещё не подтверждался пользователем.

Обратный сценарий: завершённый Cut с новой ценой $0 → Negotiate. Reported немедленно становится $900/year для переговоров, хотя цена $0 была подтверждением отмены, а не нового результата переговоров.

Доказательства: [store.ts:111](/Users/nuras/Desktop/businesscup/src/lib/store.ts:111), [money.ts:42](/Users/nuras/Desktop/businesscup/src/lib/engine/money.ts:42), [action-workspace.tsx:535](/Users/nuras/Desktop/businesscup/src/components/action/action-workspace.tsx:535).

Исправление: привязать выполнение к конкретному действию. При смене его типа сбрасывать/повторно подтверждать status, completedAt и reportedNewPrice; либо хранить выполненный результат отдельно от текущего плана. Использовать одну функцию расчёта reported в карточке и summary. Уточнить поведение при редактировании исходной цены/частоты завершённого действия: сейчас история также пересчитывается по новой базе.

### F03 Поле merchant пропускает персональные данные в LLM

ТЗ: §10.1, §11.3, NFR-04. Вердикт: реализация расходится с ТЗ. Подтверждена возможность передачи; фактическая утечка реальных данных не утверждается.

В ручное имя услуги помещена синтетическая строка `John Smith john.smith@example.com account 12345678`. Она проходит request schema и без очистки попадает в user message модели. Клиентский `buildStrictRequest` лишь обрезает имя до 80 символов. Валидация длины и список разрешённых JSON-ключей не защищают содержимое значения.

Для неизвестных импортированных описаний нормализация также не гарантирует удаления имён и email: некоторые слова и части адресов сохраняются. Переход на Action plan автоматически вызывает генерацию; отдельного действия очистки имени перед сетью нет.

Доказательства: [action-workspace.tsx:67](/Users/nuras/Desktop/businesscup/src/components/action/action-workspace.tsx:67), [schemas.ts:11](/Users/nuras/Desktop/businesscup/src/lib/schemas.ts:11), [grok.ts:47](/Users/nuras/Desktop/businesscup/src/lib/ai/grok.ts:47).

Исправление: выделить безопасное название услуги для AI отдельно от исходного описания; сомнительные/неизвестные имена просить подтвердить или заменить обобщённым названием. Проверять содержимое также на сервере. Простая regex-очистка может быть дополнительным слоем, но ТЗ прямо предупреждает, что она не гарантирует удаления ФИО. Добавить тест значения merchant, а не только списка ключей payload.

## Остальные расхождения P0

### F04 Ошибка нового импорта оставляет предыдущие данные доступными для Analyze

ТЗ: FR-04, FR-05, NFR-03. Важность: средняя. Подтверждено UI-аудитом.

После успешной загрузки CSV с тремя Netflix выбирается файл размером 5 MB + 1 byte. Видна ошибка размера, но кнопка остаётся `Analyze expenses (1)` и открывает результаты предыдущего файла. В UI одновременно существуют отказ нового импорта и готовность старого.

[import-tab.tsx:111](/Users/nuras/Desktop/businesscup/src/components/audit/import-tab.tsx:111) возвращается на ошибке, не очищая предыдущие rows/expenses. Аналогично во время нового `runParse` не блокируется анализ старого результата. Возвращаемый из `runParse` cleanup таймеров не используется обработчиками; несколько запусков могут завершиться в неправильном порядке. Этот race подтверждён чтением кода, отдельно по времени не воспроизводился.

Исправление: передавать родителю readiness/error/loading, блокировать Analyze при новом вводе и ошибке, использовать идентификатор актуального parse job и отменять старые таймеры. Старый результат можно сохранить, но только с явным выбором «использовать предыдущий файл».

### F05 Невалидная целевая цена оставляет старую экономию в итогах

ТЗ: FR-08, §8.2. Важность: средняя. Подтверждено UI-аудитом.

Netflix $15.49 → Negotiate → target $10 даёт $65.88/year. После замены target на `oops` видна ошибка, но в store остаётся `targetPriceCents=1000` и potential $65.88. Генератор также продолжит использовать прежние $10, хотя поле их уже не показывает.

Причина: [expense-card.tsx:104](/Users/nuras/Desktop/businesscup/src/components/results/expense-card.tsx:104) при ошибке только устанавливает текст ошибки. Исправление: либо очищать target в модели на невалидном вводе, либо явно различать подтверждённое значение и редактируемый черновик с сохранением/отменой. Не показывать расчёт как относящийся к текущему невалидному полю.

### F06 Изменение цены менее чем на 10 процентов скрывается и порождает неверное evidence

ТЗ: FR-06, §8.1. Важность: средняя. Подтверждено функциями.

Для Netflix $15.49, $15.49, $16.49 за три месяца выбран правильный последний тариф $16.49, но evidence утверждает `3 charges of $16.49`, confidence high, price change отсутствует. Фактически два из трёх списаний были другой суммы.

[detect.ts:156](/Users/nuras/Desktop/businesscup/src/lib/engine/detect.ts:156) считает разброс до 10% стабильным, а reason подставляет последнюю цену ко всем списаниям. Исправление: допуск для группировки не должен скрывать изменение тарифа; evidence должен описывать действительные суммы/диапазон и отдельно отмечать изменение.

### F07 Ошибки синтаксиса CSV теряются

ТЗ: FR-05, §5.3, NFR-03, T-12. Важность: средняя. Подтверждено функциями и документацией Papa Parse через Context7.

[parse.ts:43](/Users/nuras/Desktop/businesscup/src/lib/engine/parse.ts:43) использует `result.data`, но не обрабатывает `result.errors`. Строка с лишним четвёртым полем возвращается как полностью корректная, дополнительное поле незаметно отбрасывается. Незакрытая кавычка поглощает две следующие физические строки; пользователь видит одну запись с `Missing amount`, а не причину повреждения CSV и потерю последующих записей.

Papa Parse отдельно возвращает `MissingQuotes`, `InvalidQuotes`, `TooManyFields`, `TooFewFields`; наличие data не означает отсутствие ошибок. Источник: [Papa Parse](https://github.com/mholt/papaparse), Context7 `/mholt/papaparse`.

Исправление: сохранять parser diagnostics, показывать их по строкам; пригодные строки импортировать, структурно повреждённую область явно обозначать. При незакрытых кавычках не угадывать безопасное восстановление и не выдавать скрытую потерю строк за успешный импорт.

### F08 Нули в отдельных Debit и Credit ломают обработку кредитов

ТЗ: FR-04, FR-07, §7.1, T-15. Важность: средняя. Подтверждено функциями.

CSV `Debit=0, Credit=15.49` трактуется как debit с нулём и попадает в `Zero amount`, вместо входящего платежа/возврата. Это происходит потому, что строка `'0'` считается заполненной и credit не проверяется. С `Debit=''` тот же сценарий работает.

Доказательство: [parse.ts:198](/Users/nuras/Desktop/businesscup/src/lib/engine/parse.ts:198). Исправление: разобрать обе колонки численно, определить ненулевую сторону; конфликт двух ненулевых значений отправлять на review. Дополнительно в интерфейсе нет ручного выбора `debitColumn`: он заполняется только эвристикой. Для нестандартных названий отдельных колонок нужен явный mapping либо описанное ограничение.

### F09 Ручная коррекция групп и корректно разобранных строк неполная

ТЗ: FR-05, FR-08, §7.2, экран `/audit` в §9. Важность: средняя. Подтверждено кодом и UI.

У валидных строк CSV нет Fix и Skip; они появляются только у строк со статусом error. Поэтому синтаксически правильную, но содержательно неверную строку нельзя исправить/исключить в preview. На results можно изменить merchant, price, frequency и decision, но нельзя разделить ошибочно объединённые услуги или изменить состав группы. Переименование итоговой карточки состав серии не меняет.

Доказательства: [preview-rows.tsx:268](/Users/nuras/Desktop/businesscup/src/components/audit/preview-rows.tsx:268), [expense-card.tsx:95](/Users/nuras/Desktop/businesscup/src/components/results/expense-card.tsx:95). Категория доступна через возврат на manual list, что частично компенсирует её отсутствие в results editor, но не проблему группировки.

Исправление: Edit/Exclude для любых исходных строк, ручное разбиение/объединение кандидатов или управляемая группировка до анализа; изменение evidence после коррекции.

### F10 У клиента нет срока ожидания fallback и происходят лишние запросы AI

## Дополнительные рекомендации без расширения обязательного P0

**Защитить пользовательский аудит от Try demo.** UI-аудит подтвердил: добавленная `Unique family bill` исчезает из localStorage после Try demo. `loadDemo` заменяет единственную session, резервной пользовательской сессии нет. Это не отдельное прямое требование FR, но заметный риск потери работы. Предпочтительно держать sample session отдельно и давать Return to my audit; более простой вариант — явно объяснять замену до действия.

**Привести ввод денег к буквальному правилу integer cents.** [money-input.ts:13](/Users/nuras/Desktop/businesscup/src/components/money-input.ts:13) использует `parseFloat` и `Math.round(parsed * 100)`, тогда как импорт разбирает строку по цифрам. При разрешённых двух знаках и текущем cap ошибка на обычных суммах не обнаружена; это техническое отклонение от строгого запрета float, а не доказанная потеря центов. Использовать один строковый конвертер и одинаковые пределы в manual/import/API. При очень больших импортируемых значениях дополнительно проверять safe integer после annual multiplication и суммирования.

**Не выдавать print за готовый FR-18.** Results печатает текущую отфильтрованную страницу с итогами/целью, но без всех action texts. Action page печатает только активное действие, без общего финансового summary/цели. Единый PDF с полным набором полей требует отдельного report view. В README при этом написано, что PDF export отсутствует: нужно уточнить наличие базовой browser print функции и её границы.

**Уточнить политику локального сохранения.** Полный raw CSV не сохраняется, но `Expense.transactionIds` из детектора входят в persisted session. Модель §12.1 сама содержит это поле, а NFR-04 запрещает его в AI/аналитике, поэтому хранение ID не объявляется здесь однозначным нарушением исходного ТЗ. Минимизация всё же полезна: UI после анализа эти ID не использует. Нужны runtime validation/version migration persisted state и понятное сообщение при недоступном localStorage; сейчас шифрования и синхронизации нет, что допустимо и описано в README.

**Сохранить ограничения инфраструктуры явными.** In-memory rate limiter сбрасывается при cold start и не объединяет инстансы. При self-hosting IP заголовки должны приходить от доверенного reverse proxy. CSP содержит unsafe-inline для bootstrap Next; это осознанный компромисс, но не строгая nonce CSP. Для публичного масштабирования нужны централизованный лимит и политика расходов на AI. Отсутствие аккаунтов и server DB соответствует P0.

**Не обещать невозможные гарантии AI.** README утверждает, что AI никогда не выдумывает телефоны/ссылки/права возврата. Код задаёт запрет в prompt, но не гарантирует его соблюдение F11. Пока нет проверки текста, формулировку нужно смягчить и предложить пользователю проверять результат. Не требуется добавлять базу телефонов или 100 ссылок в P0.

**Обновить инженерную документацию.** [CONTRACT.md:8](/Users/nuras/Desktop/businesscup/docs/CONTRACT.md:8) всё ещё называет страницы заглушками. В описании `setActionStatus` заявлен default новой цены Cut=0, но store сохраняет undefined при отсутствии аргумента; zero подставляет money engine и UI передаёт его явно. Контракт должен описывать фактическую границу ответственности. Сама локальная копия ТЗ соответствует приложению и не требует переписывания под ошибки кода.

**Метрики ещё не реализованы.** В исходниках нет landing_viewed, audit_completed, action_text_copied и остальных событий §17.1, нет SDK аналитики. Это уменьшает риск отправки финансовых данных, но не позволит измерять North Star/конверсии. Добавлять только минимальные несодержательные события после согласования механизма аналитики; целевые 60%/40%/8–12% из ТЗ не являются текущими достигнутыми результатами.
