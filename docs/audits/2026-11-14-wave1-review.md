## W1B1 Новая регрессия распознавания двух месячных услуг

Высокая важность. [detect.ts:164](/Users/nuras/Desktop/businesscup/src/lib/engine/detect.ts:164), [detect.ts:192](/Users/nuras/Desktop/businesscup/src/lib/engine/detect.ts:192).

Синтетические операции:

| Даты | Описание | Цена | ID |
|---|---|---|---|
| 2026-08-03, 2026-09-03, 2026-10-03 | ADOBE *1 | $9.99 | Разные ID |
| 2026-08-10, 2026-09-10, 2026-10-10 | ADOBE *2 | $19.99 | Разные ID |

Оба описания нормализуются в Adobe. Ожидаются две monthly-серии и recurring 35976 cents.

Фактически новые buildChains жадно связывают 3-е и 10-е число как weekly со сменой цены, после чего разрыв до следующего месяца не подходит к weekly. Получаются три серии по две операции, weekly/low, recurring 0. То же воспроизведено при разрыве 6 и 8 дней; при 14 днях пример проходит.

Контроль: исходный detector из HEAD на том же входе возвращает две monthly/high-серии и 35976 cents. Это новая регрессия, а не только старое ограничение эвристики. Нужен выбор серии с учётом более длинной истории, а не окончательная фиксация частоты по первой подходящей паре.

## W1B2 Обход сброса completed через изменённое поле patch

Средняя важность. [lifecycle.ts:60](/Users/nuras/Desktop/businesscup/src/lib/engine/lifecycle.ts:60).

Исходный расход: Negotiate, $75 monthly, completed, reportedNewPriceCents=6000, completedAt=старое время.

`applyExpensePatch(expense, { ...expense, decision: 'cut', reportedNewPriceCents: 5999 })`

Фактически сохраняет completed, новую reported price и старое completedAt. Так же получается Keep с completed. Любое отличающееся execution-поле считается новым подтверждением, хотя пользователь отдельно новое действие не подтверждал. Это исключение не было предусмотрено заданным правилом безусловного сброса при изменении decision/исходной цены/частоты.

Нужен безусловный reset при смене базы. Подтверждение нового действия — отдельный вызов после изменения. Неактивные Keep/Not recurring/undecided не должны получать attempted/completed через публичные мутации. Тест, который сейчас требует сохранения «другого explicit confirmation» в одном patch, следует заменить тестом принятого инварианта.

## W1B3 Персональные данные в URL импортированного расхода

Высокая важность для заявленной приватности. Ранее существовавший путь, подтверждён дополнительной проверкой. [detect.ts:402](/Users/nuras/Desktop/businesscup/src/lib/engine/detect.ts:402), [expense-card.tsx:370](/Users/nuras/Desktop/businesscup/src/components/results/expense-card.tsx:370).

Синтетическое описание: `CUSTOM INTERNET JOHN SMITH john.smith@example.com account 12345678`, три месячных списания по $75.

Полученный href:

`/action?id=exp-custom-internet-john-smith-john-smith-example-account-7500`

После обычной перезагрузки страницы браузер действительно отправляет серверу GET с этим URL. Первичная SPA-навигация в контрольном прогоне не отправляла такой GET, поэтому утверждение ограничено подтверждённой перезагрузкой. Helper очистки ActionRequest не исправляет этот канал.

Нужны непрозрачные ID без имён, сумм, банковских ID и фрагментов описания. Для уже сохранённых аудитов необходима совместимая нормализация ID без потери решений/целей/статусов; версия/ключ хранения и формат ссылок должны быть учтены. Нельзя объявлять ID случайным токеном авторизации: это только идентификатор локального расхода.
