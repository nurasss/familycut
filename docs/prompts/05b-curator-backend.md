## F01 — независимые услуги и достоверное evidence

Воспроизведение: на 2026-08-03, 2026-09-03 и 2026-10-03 каждый раз два списания — `ADOBE PHOTOSHOP` $9.99 и `ADOBE ACROBAT` $19.99, с шестью разными банковскими ID. Сейчас результат: один Adobe, high, $119.88/year. Нужно сохранить две услуги и $359.76/year recurring, без автоматического Cut.

Исправь нормализацию/формирование серий: общий календарь мерчанта не должен обходить разделение продуктов/сумм, а первая транзакция за день — скрывать остальные. Различай известные услуги, в частности YouTube TV/Music/Premium. При неоднозначности снижай уверенность и показывай проверяемую причину, не придумывай продукт и не выдавай разные аккаунты за лишнюю оплату.

Сохрани обработку настоящего изменения цены одной услуги. Попутно закрой F06: $15.49, $15.49, $16.49 должны давать последнюю цену, price change и честный reason; нельзя писать `3 charges of $16.49`. Допуск близости сумм не должен скрывать изменение цены.

Регрессии: параллельные услуги; перестановка строк не меняет итог; разные YouTube-продукты; реальная смена тарифа; два списания без ID не удаляются автоматически; exact-ID dedup, refund, grocery и single annual работают как раньше. Чётко опиши, что остаётся неоднозначным.

## F02 — жизненный цикл решения и выполненного действия

Сценарий: $75 monthly → Negotiate target $60 → completed reported $60 → Cut. Сейчас сохраняется completed/6000, results показывает reported $180, а UI Cut — $900. Обратный переход completed Cut ($0) → Negotiate также ошибочно переносит выполнение.

Правило этой волны: при изменении decision сбрасывать actionStatus в not_started, reportedNewPriceCents и completedAt. Повторная установка того же decision идемпотентна и не теряет подтверждение. Изменение исходной цены/частоты завершённого действия также требует нового подтверждения: сбрасывай выполнение при фактическом изменении этих полей. Одна лишь смена target price не переписывает уже сообщённый результат того же действия. Keep/Not recurring не должны носить унаследованное completed от другого решения.

Используй общую логику для setDecision и updateExpense, чтобы patch не обходил инварианты. Не меняй принятые в ТЗ формулы и не добавляй фиктивную историю. Сохрани корректное completed с reported price и поведение Cut=0 через действующий UI. Если требуется миграция persisted state, сохраняй ключ и пользовательские данные; не очищай все аудиты для удобства.

Добавь тесты обоих переходов, идемпотентности, изменения price/frequency, reload сохранённых решений и исходного $75→$60=$180. Frontend-агент отдельно приводит отображение карточки к существующему computeTotals.

## F03 — безопасное имя услуги для AI

Синтетическая строка `John Smith john.smith@example.com account 12345678` сейчас проходит merchant schema и попадает в model user message. Whitelist JSON-ключей и slice(0,80) недостаточны. Не решай это одной regex, обещающей распознать любые ФИО.

Подготовь совместимый клиентский helper в **`src/lib/ai/safe-request.ts`**:

`buildSafeActionRequest(expense: Expense, tone: ActionTone): ActionRequest`

Он возвращает только существующие поля ActionRequest. Merchant для модели выбирается из явно разрешённых канонических имён известных сервисов; для неизвестного/неоднозначного имени используй фиксированный `Service provider`. Не считай произвольный результат normalizeMerchant безопасным только из-за нормализации. Исходное название остаётся локально для отображения; не добавляй в запрос notes/reasons/IDs/сырые строки. Helper должен быть пригоден для browser bundle, без env/server imports.

Независимо применяй ту же политику на сервере **до вызова модели**, чтобы прямой POST или старый frontend не передал произвольный merchant в LLM. Не отправляй rejected/raw значение в retry/prompts/logs. Сохрани работающий fallback и ограничения длины/enums/центов/rate limit.

В этой волне **не подключай helper в frontend**. Куратор даст отдельное интеграционное задание после проверки экспорта. В отчёте явно укажи: сервер→LLM защищён; browser→server всё ещё требует подключения helper, поэтому F03 целиком пока не принят.

Тесты: обычный известный сервис сохраняет каноническое имя; неизвестная строка с ФИО/email/телефоном/номером счёта становится Service provider; инъекция текста не попадает в модель; прямой API POST очищается независимо от клиента; helper не меняет исходный Expense. В тестах только синтетические данные и mocked fetch, без реальных LLM-вызовов.
