## 1. Резюме и рекомендация

**Рекомендуемый вариант (A): управляемая группировка строк до Analyze.** Пользователь в preview импорта выбирает *исходные строки* (`rawIndex`) и назначает их в «отдельную услугу» (Split) или «одну услугу» (Merge). Назначения живут только в состоянии вкладки импорта (как уже живут `overrides` и `skippedIndices`), передаются в `analyzeTransactions(txs, { groups })` и дают итоговые `Expense` с настоящим составом и evidence. Ничего нового не сохраняется: persisted session остаётся набором `Expense`-агрегатов, схема store и ключ не меняются, миграции нет.

Почему не вариант B (коррекция агрегатов на `/results`) и не C (хранить транзакции):

| Вариант | Что нужно | Почему отклонён / принят |
|---|---|---|
| **A. До Analyze, по строкам** | `Transaction.sourceIndex` (в памяти), `groups` в `analyzeTransactions`, UI выбора строк | **Принят.** Работает с реальными транзакциями, evidence пересчитывается по ним, ничего лишнего не хранится |
| B. Правка `Expense` на results | Разделить/склеить агрегаты | **Отклонён.** В session нет истории: `Expense` — одна цена, одна частота, список `transactionIds` (которые могут быть `row-N` и повторяться). Split пришлось бы выдумывать (какие даты и суммы у половинок?), Merge — гадать, складывать цены или нет. Нарушает «не придумывай историю» |
| C. Хранить `Transaction[]`/сырую выписку | persist новых данных | **Отклонён.** ТЗ §7.1: не импортировать лишние колонки; §11/NFR-04: минимум данных. Расширяет поверхность хранения без необходимости |

Цена варианта A: после Analyze состав группы менять нельзя — для повторной коррекции нужно заново импортировать файл/вставку. Preview не сохраняется между маршрутами (§12, Q4); UI не обещает восстановить прежние строки.

## 2. Фактический путь данных (на 14.11.2026)

| Шаг | Где | Что происходит | Важно для группировки |
|---|---|---|---|
| parse | `parseCsv`/`parsePaste` → `RawRow[]` | Строка запоминает физическую `line`; диагностика CSV привязана к объекту строки | Индекс в `rawRows` стабилен, пока не запущен новый parse |
| edit/exclude | `import-tab.tsx`: `overrides[rawIndex]`, `skippedIndices` | Исправление создаёт копию строки; исключённые строки не попадают в `applyMapping` | Идентичность строки — `rawIndex`, не `transactionId` и не `line` |
| map | `evaluateMappedRows` → `applyMapping(effectiveRows)` | `Transaction.id` = банковский ID или `row-<i+2>`; индекс **эффективных** строк ≠ `rawIndex` (скипнутые убраны); адаптер сам сопоставляет `activeIndices[effIdx]` → `rawIdx` | Адаптер — единственное место, где известен `rawIndex` транзакции |
| analyze | `analyzeTransactions(txs, { newId })` | Exact-dedup (date+merchant+amount+**реальный** ID) → refunds/credits исключаются → группировка по `merchantNormalized` → серии (`buildChains`) → `Expense` со случайным непрозрачным `id` | Каждый вызов даёт **новые случайные `Expense.id`**; ключом между пересчётами они быть не могут |
| handoff | `audit/page.tsx`: `startSession(current.expenses, { isDemo })` | **Заменяет** всю session (как и сейчас) | Группировка не нужна после этого шага: её результат — готовые `Expense` |
| persist | `store.ts`, ключ `familycut:audit:v1`, версия 2 | Только `session` и `isDemo` | Транзакций и назначений в session нет и не будет |
| results | `results/page.tsx`, `expense-card.tsx` | Показывает `reasons` одной строкой, правка merchant/price/frequency/decision | Evidence группировки показывается через `reasons` без изменений UI |

Неочевидные факты, проверенные запуском текущего `analyzeTransactions` (раздел §10 — таблица результатов):

1. Два фрагмента одной подписки (Netflix $15.49: янв–мар и июн–авг, разрыв 92 дня) сегодня дают **два** расхода, итог **$371.76/year** — удвоение. Это основной случай для Merge.
2. Два одинаковых списания в один день без ID (два аккаунта) схлопываются в **один** расход $185.88 с флагом `duplicate_candidate` («possible duplicate or two separate accounts») — для двух аккаунтов правильно $371.76. Это основной случай для Split.
3. Одна и та же подписка под разными описаниями (`NETFLIX.COM 8844` и `NFLX DIGITAL DELIVERY`) сегодня теряется: Netflix — «2 charges at irregular intervals» (low), строка `NFLX…` не попадает ни в один расход вообще. Это второй случай для Merge.
4. Последовательные разные услуги, обе обозначенные в выписке общим `ADOBE`, сегодня могут склеиваться как смена цены $9.99 → $19.99 (с пометкой «Large change»). Это случай для Split. Явные названия `ADOBE PHOTOSHOP` и `ADOBE ACROBAT` уже распознаются раздельно; не утверждаем обратного.

## 3. Понятия и действия пользователя

**Автоматическая серия** — результат текущего алгоритма (`buildChains`): цепочка списаний одной суммы с одной частотой плюс склеенные смены цены. Не меняется контрактом.

**Назначение (GroupAssignment)** — явное решение пользователя о *составе*: набор строк `rawIndices` с режимом. Строки с назначением анализируются отдельно от автоматической группировки по мерчанту. Строка принадлежит не более чем одному назначению.

**Расход (`Expense`)** — результат анализа корзины (автоматической или назначенной). Один расход = одна услуга для решений Keep/Cut/Negotiate.

| Действие | Что делает пользователь | Режим | Результат |
|---|---|---|---|
| **Разделить** (Split) | Отмечает строки, которые ошибочно попали в чужой расход, → «Treat as a separate service» | `split` | Отмеченные строки анализируются **сами по себе** как отдельная корзина обычным алгоритмом. Остальные строки мерчанта анализируются без них. Независимые услуги не теряются: итог — сумма годовых эквивалентов расходов |
| **Объединить** (Merge) | Отмечает строки (в том числе из разных расходов / разных названий мерчанта), которые являются **одной** услугой → «Treat as one service» | `merge` | Строки анализируются как одна корзина; если алгоритм всё равно получает несколько последовательных фрагментов, они сводятся в один расход по правилам §6 (цена **не суммируется**) |
| **Отменить назначение** (Undo) | «Undo grouping» у группы или «Clear all» | — | Назначение удаляется, строки возвращаются в автоматическую группировку по мерчанту |
| Переименовать карточку | Правка `merchant` на results | — | **Не изменяет состав.** Не влияет на назначения, `transactionIds`, расчёты; после Analyze назначений уже нет |
| Edit / Exclude / Restore строки | Уже принятое поведение | — | Назначение остаётся (ключ — `rawIndex`), расчёт пересчитывается (см. §8) |

Имя группы `[Согласовано куратором]`: необязательное поле `name` задаёт `Expense.merchant` результата. По умолчанию — самое частое `merchantNormalized` среди активных строк группы (при равенстве — у самой поздней строки). Это не «переименование карточки», а подпись при создании группы.

Граница ответственности: автоматические подсказки («похоже, это одна услуга») — вне P0.

### 4.2 Новый модуль `src/lib/engine/grouping.ts` (browser-safe, чистые функции)

```ts
import type { Frequency } from '@/lib/types';

export const MAX_GROUPS = 200;                 // [Согласовано куратором] защита от мусорного состояния
export const MAX_GROUP_NAME_LENGTH = 80;       // как merchant в actionRequestSchema

export type GroupMode = 'split' | 'merge';

/** Неоднозначность, которую пользователь обязан подтвердить явно. */
export type AmbiguityKind = 'large_price_change';
// Пакеты параллельных услуг отклонены для этой реализации (Q1); подтверждение не разрешает их слияние.

export type GroupAssignment = Readonly<{
  /** Непрозрачный локальный идентификатор в пределах одного preview ("g-1"). Не хранится, не уходит на сервер, не в URL. */
  groupId: string;
  mode: GroupMode;
  /** rawIndex исходных строк: целые >= 0, уникальные. Строка принадлежит не более чем одному назначению. */
  rawIndices: readonly number[];
  /** Необязательное имя результата (после normalizeGroupName). */
  name?: string;
  /** Подтверждённые виды неоднозначности; действуют только при confirmedFor === текущему proposalKey. */
  confirmed?: readonly AmbiguityKind[];
  /** Ключ конкретного показанного пользователю предложения, а не только списка индексов. */
  confirmedFor?: string;
}>;

export type GroupIssueCode =
  | 'invalid_group'        // пустой/слишком длинный groupId, неверный mode, неверные индексы
  | 'duplicate_group'      // повтор groupId: учитывается первое назначение
  | 'too_few_rows'         // merge с < 2 активных строк
  | 'unknown_row'          // rawIndex без транзакции с sourceIndex
  | 'row_excluded'         // строка исключена/ошибочна/refund/credit/exact-дубликат — назначение её не возвращает
  | 'row_in_other_group'   // строка уже занята более ранним назначением
  | 'invalid_name'         // имя не прошло normalizeGroupName; используется автоматическое
  | 'mixed_periods'        // последовательные части с разными частотами: сложить в одну цену нельзя
  | 'overlapping_services' // части идут параллельно: суммировать нельзя (см. §6, Q1)
  | 'needs_confirmation'   // нужна явная подтверждающая отметка
  | 'amount_too_large'     // цена результата > MAX_AMOUNT_CENTS
  | 'no_expense';          // строки не образуют регулярный расход (информационно)

export type GroupIssue = {
  code: GroupIssueCode;
  severity: 'info' | 'warning' | 'error';
  /** Короткий текст для пользователя, английский (TZ NFR-08). Не содержит исходных описаний транзакций. */
  message: string;
  rawIndices?: number[];
};

export type GroupStatus =
  | 'applied'             // назначение действует
  | 'needs_confirmation'  // не действует, пока нет подтверждения; строки пока анализируются автоматически
  | 'rejected'            // не действует и не может быть подтверждено (mixed_periods, amount_too_large, …)
  | 'inactive';           // не действует: после исключений осталось слишком мало активных строк

/** Что получится, если назначение применить — для текста подтверждения в UI. Деньги — целые центы. */
export type GroupProposal = {
  /** Детерминированная ревизия предложения; не зависит от случайных Expense.id, newId или confirmed. */
  proposalKey: string;
  merchant: string;
  priceCents: number;
  frequency: Frequency;
  annualCents: number;     // priceCents * MULTIPLIER[frequency], как в money.ts
  chargeCount: number;
  partCount: number;       // число последовательных фрагментов истории
  gapDays: number[];       // разрывы между фрагментами, дни
  requires: AmbiguityKind[];
};

export type GroupReport = {
  groupId: string;
  status: GroupStatus;
  /** rawIndex строк, реально вошедших в анализ этого назначения. */
  activeRawIndices: number[];
  ignoredRawIndices: { rawIndex: number; reason: 'unknown_row' | 'row_excluded' | 'row_in_other_group' }[];
  issues: GroupIssue[];
  /** id расходов, получившихся из назначения (пусто для needs_confirmation/rejected/inactive/no_expense). */
  expenseIds: string[];
  proposal?: GroupProposal;
};

/** Состав каждого расхода по исходным строкам: единственная точка связи «расход → строки preview». */
export type ExpenseSource = {
  expenseId: string;
  /** sourceIndex транзакций расхода, по возрастанию. Строка встречается не более чем в одном расходе. */
  sourceIndices: number[];
  /** Если расход получен из назначения. */
  groupId?: string;
};
```

### 4.3 Операции над назначениями (состояние UI, чистая функция)

```ts
export type GroupOp =
  | { type: 'split'; rawIndices: readonly number[]; name?: string }
  | { type: 'merge'; rawIndices: readonly number[]; name?: string }
  | { type: 'confirm'; groupId: string; kinds: readonly AmbiguityKind[]; proposalKey: string }
  | { type: 'undo'; groupId: string }
  | { type: 'clear' };

export type GroupOpError =
  | 'no_rows' | 'too_few_rows' | 'too_many_rows' | 'invalid_index'
  | 'invalid_name' | 'unknown_group' | 'too_many_groups' | 'invalid_confirmation';

export type GroupOpResult =
  | {
      ok: true;
      assignments: GroupAssignment[];
      /** Созданное/изменённое назначение (для split/merge/confirm). */
      groupId?: string;
      /** Назначения, исчезшие из-за переноса строк или опустевшие. */
      removedGroupIds: string[];
    }
  | { ok: false; error: GroupOpError; message: string };

/** Не мутирует вход. makeGroupId по умолчанию даёт "g-<n>" (n = наименьшее свободное). */
export function applyGroupOp(
  assignments: readonly GroupAssignment[],
  op: GroupOp,
  makeGroupId?: () => string,
): GroupOpResult;

/** Trim, схлопывание пробелов, 1..80 символов, без управляющих символов; иначе null. */
export function normalizeGroupName(input: string): string | null;
```

Правила `applyGroupOp`:

1. `split`/`merge` **забирают** строки из любых других назначений (строка в одном назначении). Опустевшее назначение, а также `merge`-назначение, у которого осталась 1 строка, удаляется (`removedGroupIds`). У затронутых назначений `confirmed` и `confirmedFor` сбрасываются.
2. `rawIndices` дедуплицируются и сортируются; пустой набор → `no_rows`; `merge` менее чем с 2 строками → `too_few_rows`; индекс не целое неотрицательное → `invalid_index`; > 10 000 → `too_many_rows`; групп > `MAX_GROUPS` → `too_many_groups`.
3. `confirm` записывает разрешённые виды в `confirmed` и переданный `proposalKey` в `confirmedFor`; неизвестная группа → `unknown_group`. Пустой ключ → ошибка `invalid_confirmation`. Изменение назначения обнуляет оба поля. Движок сравнивает ключ с текущим предложением, поэтому изменение даты/суммы/активности строки с прежними rawIndices не сохраняет старое подтверждение (§14).
4. `undo` удаляет назначение (неизвестная → `unknown_group`); `clear` удаляет все.
5. Операции не знают о статусах строк (valid/excluded/error): это забота `analyzeTransactions` (`ignoredRawIndices`) и UI (какие чекбоксы доступны).

## 5. Правила валидации и обработки ошибок

`analyzeTransactions` никогда не бросает исключение из-за `groups`: некорректное назначение превращается в `GroupReport` со статусом и `issues`; остальной анализ идёт как без него.

| Правило | Поведение | `status` / `code` |
|---|---|---|
| `groupId` пуст, длиннее 40 символов, режим не `split`/`merge`, индекс не целый ≥ 0, повтор индекса внутри группы | дубли индексов схлопываются; остальное — отклонение | `rejected` / `invalid_group` |
| Повтор `groupId` | действует первое, повторы игнорируются | `rejected` / `duplicate_group` |
| `rawIndex` без транзакции с `sourceIndex` (ошибочная/исключённая строка, чужой индекс) | строка не в анализе; назначение дальше действует на остальных | `ignoredRawIndices: unknown_row` |
| Переданная транзакция — refund, входящий кредит или exact-дубликат (удалён dedup'ом) | **Назначение не возвращает строку в расходы** | `ignoredRawIndices: row_excluded` |
| Строка уже в более раннем назначении массива | ранее назначение выигрывает (UI через `applyGroupOp` таких конфликтов не создаёт) | `ignoredRawIndices: row_in_other_group` |
| `merge`: активных строк < 2 | не действует; при Restore/Edit строки снова активны | `inactive` / `too_few_rows` |
| `split`: активных строк ≥ 1 | действует. Результат без регулярного расхода (одиночная строка магазина) — не ошибка | `applied` + `no_expense` (info), `expenseIds: []` |
| `name` не прошёл `normalizeGroupName` | имя игнорируется, берётся автоматическое | `invalid_name` (warning) |
| `merge`: последовательные части с разными частотами (§6) | отклоняется, подтверждения нет | `rejected` / `mixed_periods` |
| `merge`: части параллельны (§6) | отклоняется (P0) | `rejected` / `overlapping_services` |
| `merge`: скачок цены между частями > 1.5× (тот же порог `LARGE_CHANGE_RATIO`, что в `detect.ts`) без `confirmed: ['large_price_change']` с совпадающим `confirmedFor` | строки пока анализируются автоматически; в `proposal` — что получится | `needs_confirmation` / `needs_confirmation` |
| Цена результата > `MAX_AMOUNT_CENTS` (100 000 000 ¢) | отклоняется | `rejected` / `amount_too_large` |
| `confirmed` содержит вид, который не нужен | игнорируется | — |

Инварианты (проверяются тестами, §11):
- **I1.** Каждый `sourceIndex` входит не более чем в один расход (`ExpenseSource`), одна строка не увеличивает расход дважды.
- **I2.** Члены расходов — только активные расходные строки: refunds, кредиты и exact-дубликаты не входят никогда.
- **I3.** Без `groups` результат (кроме случайных `id`) совпадает с текущим побайтно; с пустыми `groups: []` — тоже.
- **I4.** Результат не зависит от порядка строк и порядка назначений (кроме `row_in_other_group`).
- **I5.** Все суммы — целые центы; `priceCents` ≤ `MAX_AMOUNT_CENTS`; формулы `computeTotals` не меняются.
- **I6.** `ExpenseSource.expenseId` ссылается на существующий расход; `GroupReport.expenseIds` — на расходы из `expenses`.

## 6. Правила цены и частоты

Общее: `annualCents = priceCents × MULTIPLIER[frequency]` (§8.1 ТЗ), цена = последнее списание. Цены разных периодов **никогда** не складываются в одну цену; расходы разных услуг складываются только на уровне годовых итогов (`computeTotals`), а не как один `priceCents`.

### 6.1 Split (`mode: 'split'`)

Строки назначения анализируются обычным алгоритмом **независимо** от остальных строк мерчанта; остальные строки — тоже без них. Из назначенной корзины может получиться и несколько расходов (если там несколько услуг — пользователь может разделить ещё раз). Цена и частота каждого расхода — по его собственным списаниям.

### 6.2 Merge (`mode: 'merge'`)

Строки назначения анализируются как одна корзина обычным алгоритмом. Пусть получилось *k* серий.

| *k* и взаимное расположение серий | Результат |
|---|---|
| **k = 1** (например `NETFLIX.COM` и `NFLX DIGITAL` образуют одну месячную цепочку) | Обычный расход. Это основной случай слияния разных названий |
| **k ≥ 2, диапазоны дат не пересекаются** («последовательные фрагменты») | **Один** расход: частота — полоса серий, у которых она определена; цена — **последнее** списание самой поздней части (не сумма); число списаний — общее; `annualCents = price × mult` один раз. Одиночные списания не задают частоту |
| те же, но у частей с частотой *разные* полосы | `rejected` / `mixed_periods` — ни одна «месячная цена» не получится |
| те же, цена скачет > 1.5× между частями | `needs_confirmation` (`large_price_change`): без подтверждения слияния нет |
| частота нигде не определена (одиночные списания с разрывами вне полос) | Расход с `frequency: 'unknown'`, `confidence: 'low'`: по правилам `computeTotals` не считается регулярным, пока пользователь сам не задаст частоту и решение |
| **k ≥ 2, диапазоны пересекаются** («параллельные услуги») | `rejected` / `overlapping_services` (P0). Параллельные услуги автоматически уже остаются отдельными расходами — суммарный годовой итог тот же (пример 3). Вариант «пакет услуг» — Q1 |

Автоматическая подпись `merchant` для `merge`: `name` или самое частое `merchantNormalized` (при равенстве — самой поздней строки).

### 6.3 Примеры расчёта (суммы по `computeTotals`, центы)

Данные примеров синтетические; блок «Сегодня» получен запуском текущего `analyzeTransactions` 14.11.2026 (§10).

**Пример 1 — Split: два аккаунта Netflix, одинаковые списания в один день, без ID.**
Строки 0–5: 3 месяца × 2 одинаковых списания $15.49 (`2026-08-03/09-03/10-03`).
- Сегодня: **один** расход $15.49 monthly, `duplicate_candidate`, recurring **$185.88**.
- `split` строк {1, 3, 5}: корзина A {0, 2, 4} → Netflix $15.49 monthly, 3 списания (high); корзина B {1, 3, 5} → Netflix $15.49 monthly, 3 списания (high). Флага `duplicate_candidate` у обоих нет (одинаковых списаний в корзине нет).
- Итог: **два** расхода, recurring = 2 × 1549 × 12 = **37176** ($371.76). Если пользователь ничего не делает — остаётся флаг-подсказка и $185.88 (поведение не меняется).

**Пример 2 — Merge: два последовательных фрагмента Netflix.**
Строки: `2026-01-03, 02-03, 03-03` и `2026-06-03, 07-03, 08-03`, все $15.49, одно название.
- Сегодня: **два** расхода по $15.49 (high), recurring **$371.76** (удвоение: разрыв 92 дня не вписывается в месячную полосу).
- `merge` всех 6 строк: k = 2, диапазоны не пересекаются, обе части monthly, цена одинакова → **один** расход: $15.49 monthly, 6 списаний, `confidence: 'medium'` (потолок для слияния через разрыв), reasons: `Grouped by you: 6 charges in 2 parts`, `Gap of 92 days between parts — months may be missing from the statement`.
- Итог: 1549 × 12 = **18588** ($185.88), не 37176.

**Пример 3 — Adobe $9.99 и $19.99, обе monthly, параллельно.**
- Автоматически (уже сегодня): два расхода, recurring 999×12 + 1999×12 = 11988 + 23988 = **35976** ($359.76).
- `merge` этих строк: `rejected` / `overlapping_services`, результат не меняется (**35976**). Сумма 9.99 + 19.99 как «одна месячная цена» не создаётся. (При ответе «да» на Q1: расход «пакет» $29.98 monthly, annual 2998 × 12 = **35976** — тот же итог, но требует подтверждения.)
- Если части *последовательны* (Photoshop мая–июля, Acrobat августа–октября, шесть списаний), сегодня это **один** расход $19.99 («Price changed $9.99 → $19.99», «Large change») = **23988**. Пользователь, знающий, что это две услуги, делает `split` строк Acrobat: два расхода, 11988 + 23988 = **35976** (Photoshop дальше он сам помечает Not recurring, если подписка закончилась — вывод остаётся за ним).

**Пример 4 — разные периоды.**
Adobe monthly $9.99 (3 списания) + годовой фрагмент $99.99 *до* них (два списания 2024–2025 с разрывом года): `merge` → части последовательны, полосы `monthly` и `yearly` различны → `rejected` / `mixed_periods`. Расходы остаются раздельными: 11988 + 9999 = 21987 (годовая часть — по собственным данным). Никакая «месячная цена» из них не строится.

**Пример 5 — подтверждение скачка цены через разрыв.**
Две последовательные monthly-части с разрывом, который алгоритм сам не склеивает: $9.99 в `2026-01-03, 02-03, 03-03`, затем $19.99 в `2026-06-03, 07-03, 08-03` (разрыв 92 дня). Пользователь делает `merge` → k = 2, цена 2.0× → `needs_confirmation`; `proposal = { priceCents: 1999, frequency: 'monthly', annualCents: 23988, chargeCount: 6, partCount: 2, gapDays: [92], requires: ['large_price_change'] }`. До `confirm` расходы считаются автоматически (два расхода: 11988 + 23988 = 35976); после — один расход $19.99 monthly, `Price changed from $9.99 to $19.99`, confidence ≤ medium, итог **23988**. Если же те же цены идут подряд без разрыва (пример 3, последовательный случай), алгоритм уже сам объединяет их в одну серию с пометкой «Large change», и подтверждение при слиянии не требуется: оно нужно только там, где слияние *принудительно* соединяет части через разрыв.

## 7. Evidence, confidence, flags, принадлежность транзакций

Принцип: показывать только то, что есть в строках. Истории между фрагментами не придумывается («месяцы пропущены» — предположение, оно так и формулируется).

| Что | Правило |
|---|---|
| `reasons` | Сохраняются обычные строки алгоритма (число списаний, интервал, `Price changed…`, `Amounts seen…`). Первой добавляется строка источника **[Согласовано куратором]**: split — `Separated by you: treated as its own service`; merge — `Grouped by you: N charges in K parts` (для k = 1 — `Grouped by you: N charges`). Для разрывов между частями — `Gap of D days between parts — months may be missing from the statement`. Строк с описаниями транзакций, суммами не из списаний, номерами аккаунтов нет |
| `confidence` | Базовые правила не меняются (`baseConfidence` по числу реальных списаний и частоте). Merge с разрывом (k ≥ 2): потолок **medium** (никогда high, никогда `manual`). Split: без потолка — честные правила по назначенным строкам (одна строка = low). `manual` остаётся только для введённых вручную расходов |
| `flags` | Новых значений `SystemFlag` **нет** (schema не меняется). `duplicate_candidate` ставится только если в самой корзине есть одинаковые списания в один день; `price_increase` — по обычным уровням цены. Эффект: split убирает флаг у разведённых аккаунтов |
| `transactionIds` | Ровно `id` транзакций-членов в хронологическом порядке. Могут повторяться (неуникальные банковские ID) или быть `row-N` — это информация, не идентичность |
| Принадлежность | Идентичность строки — `sourceIndex` (rawIndex). Связь «расход → строки» только через `ExpenseSource`. Dedup, refunds/credits отрабатывают **до** назначений и независимо от них: назначение не возвращает исключённую строку и не отменяет exact-дедуп (ключ date+merchant+amount+реальный ID) |
| `alongside`-пометка параллельных услуг | Считается внутри корзины. Назначение не создаёт и не убирает пометок у расходов из других корзин того же мерчанта |
| Деньги | Целые центы; `MAX_AMOUNT_CENTS`; формулы `computeTotals` и `annualCents` без изменений |

## 8. Жизненный цикл и поведение

| Событие | Поведение |
|---|---|
| Ошибка назначения (`rejected`, `needs_confirmation`, `inactive`) | Не меняет результат (строки анализируются автоматически); причина показывается у группы. **[Согласовано куратором]** `needs_confirmation` и `rejected` блокируют Analyze, пока их не подтвердят/не отменят, чтобы намерение пользователя не пропало молча; `inactive` не блокирует (Q2) |
| Отмена | `undo` одной группы / `clear` — состав возвращается к автоматическому; ничего не остаётся в хранилище |
| Edit строки | Назначение сохраняется по rawIndex; UI сбрасывает confirmed/confirmedFor затронутых групп. Engine независимо сравнивает proposalKey по текущим данным: прежнее подтверждение не разрешает новое предложение. Ошибочная строка отсутствует в txs и даёт unknown_row; UI уточняет причину по своему preview |
| Exclude / Restore | Назначение остаётся, но подтверждение затронутой группы сбрасывается при каждом действии. Пропущенная строка отсутствует в txs (unknown_row); Restore возвращает её. Engine проверяет ключ нового предложения. merge с < 2 активными строками — inactive |
| Новый файл / вставка / Load sample / Retry parse | `rawIndex` меняют смысл → **все назначения очищаются** вместе с `overrides` и `skippedIndices` (как `clearPreviewState`) |
| Смена mapping (колонок/знака) | **[Согласовано куратором]** назначения очищаются с короткой подсказкой («Grouping was cleared because the columns changed»): даты/суммы строк перечитаны, прежняя группировка могла стать неверной (Q7). `overrides`/`skippedIndices` ведут себя как сейчас |

| Analyze | Для импорта при непустой реальной session требуется отдельное подтверждение Replace audit: заменяются расходы, решения, reported savings и цель. Cancel сохраняет session и preview. Для manual-перехода и замены demo подтверждение не нужно. Перед заменой повторно проверяются актуальные readiness и результат. Сохраняются только новые Expense с непрозрачными ID, без groups/sourceIndex/raw rows |
| Изменение состава после Analyze | Для P0 нужно заново импортировать данные (Q4). Назначения не переживают unmount. Новая session содержит новые расходы undecided/not_started без reported/completedAt; старые action-ID дают Expense not found |
| Если когда-нибудь добавят правку состава на results | Любое изменение состава должно сбрасывать выполнение через `lifecycle.ts` как смену базы (`resetExecution`) — вне этого контракта |
| AI и приватность | В `ActionRequest` ничего нового не попадает: `groupId`, `rawIndices`, `sourceIndex`, `name`, `reasons` не отправляются. `name` и `merchant` проходят существующую политику `safe-request` (неизвестное имя → `Service provider`). E2E проверяет фактический payload |
| Хранение | Raw CSV, `merchantRaw`, лишние колонки не сохраняются; persist-схема не меняется; миграция **не нужна** |

2. Вставка двух фрагментов Netflix: Merge → одна карточка, $185.88/year, текст «Grouped by you…» и «Gap of 92 days…», итог не $371.76.
3. Merge Adobe $9.99 + $19.99 параллельно: сообщение об отказе, итог остаётся $359.76; скачок цены → окно подтверждения с суммами из `proposal`, без подтверждения Analyze заблокирован.
4. Edit/Exclude/Restore: правка суммы в группе пересчитывает итог; Exclude строки меняет состав и статус группы; Restore возвращает.
5. Смена файла/вставки/mapping очищает группы (с подсказкой для mapping); Delete my data очищает состояние и ничего не оставляет в `localStorage`.
6. Analyze → `/results` → reload: расходы и evidence сохранены, в `localStorage` нет `rawIndices`/групп/сырых описаний; Cut на сгруппированном расходе и POST `/api/ai/action` содержат только поля `ActionRequest`, `Service provider`/каноническое имя, без индексов и групп.
7. Доступность: выбор строк чекбоксами с клавиатуры, статусы групп не только цветом, подтверждение — управляемый диалог; 360/375 px без горизонтального скролла.
8. Ссылки: старый `/action?id=` после повторного Analyze показывает Expense not found без POST.

## 12. Решения куратора (14 ноября 2026)

Список [Согласовано куратором]: режимы Split/Merge и поля `GroupAssignment`; `Transaction.sourceIndex` в памяти; `name` группы; потолок confidence `medium` для слияния через разрыв; пороги подтверждения (скачок > 1.5×); блокировка Analyze при `needs_confirmation`/`rejected`; очистка назначений при смене mapping; строки evidence в `reasons`; отказ `overlapping_services` в P0.

## 13. Ограничения контракта

- Контракт описывает поведение, а не реализацию: внутреннее устройство `buildChains`/`describe` меняет Claude в backend-этапе, существующие тесты должны остаться зелёными без правок.
- Примеры §6.3 и таблица §10 — синтетические; блок «Сегодня» получен фактическим запуском, блоки «нужно» — ожидаемый результат реализации, не подтверждённое поведение.
- Эвристики серий остаются эвристиками: назначение пользователя переопределяет *состав*, но не доказывает, что услуга активна или что месяцы пропущены.
- Полная проверка доступности и реальных мобильных браузеров этим контрактом не заменяется; P0 в целом не объявляется завершённым.


## 14. Уточнения при приёмке (имеют приоритет)

1. **Ревизия подтверждения.** proposalKey детерминированно зависит от фактического активного состава, дат, сумм, нормализованных мерчантов, режима, подписи и параметров показанного предложения. Он не включает случайные Expense.id/newId, время и собственно confirmed. Это локальный ключ согласованности, не auth-токен; он не сохраняется, не попадает в URL/AI. Любое релевантное изменение меняет ключ. Engine принимает confirmed только при точном совпадении confirmedFor и нужного вида. Сценарии Edit суммы/даты с теми же rawIndices и Exclude → confirm → Restore проверяются отдельными unit/E2E. UI дополнительно очищает подтверждения при Edit/Exclude/Restore; старое подтверждение не воскресает при возврате старых значений.
2. **Merge через разные названия.** Корзина Merge получает единый внутренний ключ анализа после глобальных dedup/refund/credit-фильтров. Обычная группировка по прежним merchantNormalized внутри неё не должна снова разнести эти строки. Исходные Transaction не мутируются. name — подпись результата, не доказательство частоты/активности и не способ превратить магазин в подтверждённую подписку. Проверка частей выполняется до отбрасывания нерегулярных/неизвестных фрагментов через describe: пропавший из автоматического результата NFLX не теряется при явном Merge.
3. **Границы источников.** sources строится при создании расходов по фактическим объектам транзакций, не восстанавливается обратным поиском transactionIds. При повторяющемся/некорректном sourceIndex ручное назначение на такой индекс отклоняется как invalid_group без молчаливого выбора объекта. Отсутствующие в txs строки (skip/parse error/чужой индекс) дают unknown_row; только переданные, но отфильтрованные engine транзакции дают row_excluded. UI может уточнять текст по собственному состоянию строк.
4. **Автоматический пул.** Только applied-группы забирают строки из автоматического анализа. needs_confirmation/rejected/inactive не должны терять расходы. В автоматический пул попадает каждая оставшаяся eligible-строка максимум один раз; занятые действующей группой строки там отсутствуют. Конфликтные назначения из некорректного внешнего массива обрабатываются по порядку с явным row_in_other_group, без двойного учёта. Для точных дублей с sourceIndex выбирается детерминированный представитель; перестановка txs с сохранёнными sourceIndex не меняет принадлежность.
5. **Частота и доказательства.** Merge разных названий не создаёт частоту из имени. mixed_periods и overlapping_services остаются отклонением, а не подтверждаемой неоднозначностью. Большой скачок требует подтверждения только для принудительного соединения разорванных частей (§6), без изменения прежнего автоматического k=1-пути. Факты частей, последние суммы и разрывы доступны до построения итогового reason; нельзя писать, что все N списаний имели последнюю цену, если это неверно.
6. **Проверки совместимости.** Без groups и с groups=[] прежние expenses/stats и экономические результаты сохраняются. Поля sources/groups аддитивны. Старые автоматические находки из §10 не исправляются глобальной сменой детектора в этой задаче; пользователь может скорректировать их назначением.
7. **Дополнение критериев приёмки.** Проверяются stale-confirmation после Edit/Exclude/Restore, неоднозначный sourceIndex, отсутствующая строка, совпадающие банковские ID, Merge разных названий и сохранение фактических sourceIndices при перестановке. Gemini проверяет замену реальной session: Cancel сохраняет данные/цель, Replace создаёт новую session без старых подтверждений, а старые action links не отправляют AI-запросы.
